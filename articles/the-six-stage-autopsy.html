The Six-Stage Autopsy

Agent failures show up in one stage and start in another. This is the method every field report on this site uses to tell the two apart.

Research window 2026-07-01 → 2026-10-06Audience anyone debugging agents1 sourced study + 22 field reportsentry point

01The Setup

Every agent postmortem starts with a symptom: a wrong answer, a duplicate charge, an empty search, a test that never existed. The symptom has a location, the place in the run where someone finally noticed. Teams fix that location. They add a prompt rule, a retry, a stronger model. The bug comes back wearing different clothes.

The reports on this site all make the same move: separate where a failure surfaced from where it started, and fix the second one. This page explains the tool used to do that, so you can run it on your own traces.

02The Reframe

"Which stage failed?" is the wrong question, because the stage that failed visibly is usually innocent. Ask instead: at which stage did the run first become wrong, and what component owns that stage?
Before"The agent gave a bad answer, so the model reasoned badly."
After"The answer was the last stage to hold a bad state that entered three stages earlier."
TurnDebug the first wrong stage, not the last visible one.

03The Six Stages

Coined termSix-stage autopsy: walking a failed agent run through planning, tool_call, retrieval, execute, verify and output, and marking the first stage whose state was already wrong (the root) separately from the stage where the failure was noticed (the symptom).
StageWhat it ownsTypical root-cause question
planningDecomposition, task graphs, delegation, constraints carried from the requestWas the plan binding, and did it carry every hard constraint?
tool_callTool selection, argument binding, tool manifests and schemasDid the tool contract the model saw match the one that ran?
retrievalContext assembly: memory, RAG, instruction files, results passed between agentsWhat was in context, where did it come from, and was it still true?
executeSide effects, state commits, retries, resume, sandboxing: the harnessDid each external effect happen exactly as many times as intended?
verifyEvals, guardrails, tests, reviewDid the check look at the layer where this failure lives?
outputFinal delivery, summaries, handoffs to humans or other agentsDoes the handoff describe what actually happened?

04Execution Trace: How to Read One

Autopsy procedure · any failed run
  1. planning ← first wrong state?Write down the state the run should have at the end of this stage. Compare it with the trace. If they already differ, stop: this is your root.
  2. tool_callSame check: the expected tool, arguments and manifest against what was actually sent.
  3. retrievalExpected context against actual context. Diff the prompt, not the summary of it.
  4. executeExpected external effects against actual ones, counted at the boundary, not from the agent's log.
  5. verifyWhich layer did the check inspect? Was this failure visible from there?
  6. output ← usually where you startThe symptom. Record it, then walk back up from the top rather than down from here.

Walk top-down. The first stage whose actual state diverges from the expected state is the root; everything after it is propagation.

05The Evidence

arXiv 2607.28802 · 2026-07-30

“Model or Harness? An Interaction-Centric Taxonomy for Localizing Agent Failures”

The authors argue that existing evaluations collapse agent failures into system-level outcomes, which hides where a fault started and which intervention would help. The same visible failure might need model post-training, harness engineering, environment redesign or benchmark repair. Their taxonomy organises 41 failure modes drawn from public benchmarks, system cards and agent logs. It localises each failure to the interaction where it originates and assigns a fault side (model, harness, environment or grader). Independent judges recovered human labels with Cohen's κ = 0.76.

Same principle: localise origin, not outcome

The hidden connection

The six stages are a working engineer's version of the same idea. They're coarser than a 41-mode taxonomy, but small enough to hold in your head during an incident. Every report below applies it to one recurring failure and names the pattern so you can recognise it next time.

06Argue the Other Side

Real failures often have more than one cause. A stale index (retrieval) and a lenient schema (tool_call) and a shallow eval (verify) can all be necessary for a bad outcome. Picking one "root" can hide the others, and stages blur in practice: is a retry policy part of tool_call or execute?

Both are true. The autopsy doesn't claim there's one cause. It claims there's one first divergence, and that fixing it usually removes the most downstream symptoms per line of code. Note the other contributing stages too. A useful rule: fix the root, and add a check at the verify stage that would have caught it.

08Autopsy Checklist

  • Capture the full trace: prompts as sent, tool manifests, tool arguments and results, external effects, check results.
  • Write the expected end-state for each of the six stages before reading the trace, so the symptom doesn't anchor you.
  • Walk top-down and mark the first divergence as root. Mark where it was noticed as symptom.
  • Name the owning component (model, harness, tool contract, data, check) and fix it there.
  • Add a verify-stage check that would have caught this root, so the next one fails loudly.
  • Record root_cause_stage and symptom_stage in your incident log. Patterns show up within weeks.
# a minimal autopsy record — one per incident
{
  "incident": "2026-10-02-duplicate-renewal",
  "symptom_stage": "output",
  "root_cause_stage": "execute",
  "owner": "tool-contract",          // model | harness | tool-contract | data | check
  "first_divergence": "charge executed twice after client timeout",
  "new_check": "count external charges per run_id == 1"
}

09Recall Check

What's the difference between the root stage and the symptom stage?

The root is the first stage whose state was already wrong. The symptom stage is where someone noticed. Fixing the symptom stage usually just moves the failure.

Why walk the trace top-down instead of from the symptom backwards?

Starting from the symptom anchors you on the visible stage. Comparing expected and actual state from planning onwards finds the first divergence directly.

What four fault sides does the 2607.28802 taxonomy assign?

Model, harness, environment and grader.
