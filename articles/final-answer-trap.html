The Final Answer Trap

On March 12, Cognition Labs introduced Devin. The demo showed the AI software engineer fixing an Upwork bug. Viewers watched the final patch. It compiled. The internet called it a breakthrough. Days later, engineers dissecting the screen recording found a different story. The agent had searched the repository, missed the correct C++ file, and retrieved an unrelated Python script. It then spent five minutes editing the wrong file before stumbling onto a partial fix. The final output passed. The execution trajectory was a disaster.

If you evaluate only the terminal output, you are measuring an accident, not a system. A passing final answer is the worst possible signal of agent capability.

[BEAT 1] The final output is a mirage; the execution trace is the water table. When you score a final patch, you cannot distinguish between an agent that executed a flawless retrieval path and one that hallucinated its way into a syntactically correct file. You reward the collision of errors that happened to produce a green test.

The Princeton SWE-agent team recognized this dynamic later in March. They didn't just tune prompts; they built an Agent Computer Interface (ACI). Their research showed that standard evals missed trajectory failures. An agent would hallucinate a file path, write to it, and fail later.

By instrumenting the retrieval and execution layers, they caught the hallucination before it contaminated the output. The ACI design forced the agent to verify its retrieval steps. Your brain's prediction-error circuitry flags unexpected outcomes for conscious review, which is why a failed tool call grabs your attention faster than a successful one. Agents need this same feedback loop embedded in their execution loop to self-correct.

Standard LLM evals check the final answer. Agent evals must check the trajectory. Final-answer evals create an illusion of competence. You ship an agent that passes every test in your staging environment. It fails in production multi-step use because the environment shifts, the accidental side-effects stop aligning, and the agent has never learned to correct a bad retrieval step.

If the task is done, who cares? Accidental successes do not generalize; they break catastrophically when the environment shifts.

[BEAT 2] You aren't training an agent to be right; you are training it to fail safely. A trajectory-level eval exposes the exact layer where the agent lost the plot. Did it plan correctly but fail at tool formatting? Did it format the tool call but retrieve the wrong file? Did it retrieve the right file but edit the wrong line? Without this granularity, your debugging is blind. You will spend hours fixing a tool-call syntax when the upstream retrieval failure was the actual culprit.
