The Retry Echo

Your agent didn't double-charge the customer because it reasoned badly. It retried a write it had no way to observe, so exactly-once belongs at the write boundary, not in the prompt.

Research window 2026-07-01 → 2026-10-06Audience agent systems engineers3 sourced storiesroot cause: execute

01The Setup

Composite scenario, assembled from the incident patterns documented in the sources below.

A renewal agent has three tools: charge_customer, grant_entitlement and send_receipt. On a Tuesday, the payment provider's API slows down. The charge call times out after 30 seconds. The agent sees an error, reasons, correctly, that the renewal hasn't been confirmed, and calls charge_customer again. The second call succeeds. So did the first: it landed on the provider's side three seconds after the client gave up.

The team's postmortem starts in the obvious place. They read the trace, see the model "decide" to retry, and add a line to the system prompt: never retry a payment call. A week later a different timeout leaves a renewal half-done, because the agent now refuses to retry a charge that genuinely never happened. They have swapped double charges for missed renewals.

Which component failed: the model that retried, or the system that gave it nothing to look at before deciding?

02The Reframe

Duplicate side effects are not a reasoning failure. They are a contract failure at the execute boundary. When nothing in the system can tell the agent whether a write landed, no prompt makes the right choice reliably.
Before"The model retried when it shouldn't have, so we need a smarter model or a stricter prompt."
After"The model had to guess, because the tool offered no idempotency key and no read-back."
TurnExactly-once is a property of the write path. You can't instruct it into existence.

03The Mechanism

Coined termRetry echo: a duplicate side effect produced when an agent or its harness re-issues a write whose first outcome it could not observe.

A tool-using agent stacks two retry layers. The harness retries at the transport level: a timeout, a 5xx, a dropped connection. The model retries at the reasoning level: it reads an error string and decides to try again. Neither layer knows whether the server already executed the request. A timeout tells you the client stopped waiting, not that the server stopped working.

That leaves two kinds of fault. In the first, the outcome is recoverable: a read-back such as get_charge(customer, period) can show what happened, and a capable model told to act exactly once will check first. In the second, the outcome is unobservable: the request is still in flight, or the transport delivered it twice, or the read path is eventually consistent. Here, the model is choosing between a duplicate and a skipped step with no information. Better reasoning can't fix that.

Durable execution makes it worse in a way most teams don't expect. When a checkpointing framework resumes after a crash, it has to decide what "resume" means for effects that had already fired. If it replays the last step, every write in that step echoes.

05The Evidence

arXiv 2609.29095 · Jiapeng Li · Sep 2026

The model matters only when the outcome is observable

The paper builds Limbo, a deterministic sandbox of six services and twelve fault modes, and runs 25,930 episodes across nine recent models, three production agent harnesses and two contract variants. When an immediate read-back can reveal what happened, frontier models told to act exactly once almost never duplicate a lost-acknowledgement write (0.5%), and the model explains 53% of the explained variance. When it can't (request still in flight, or delivered twice), the same frontier models duplicate in 56% and 74% of episodes, and the tool contract explains 81%. Offering an idempotency key on every write cut the duplicate rate from 28% to 4%. The harness barely mattered.

Failure stage: execute (write contract)

arXiv 2608.03836 · Sajjad Khan · Aug 2026

"Resume" means different things in different frameworks

Resume Means Resume defines a six-property contract for checkpoint, interrupt and resume semantics, including effect exactly-once, and model-checks it in TLA+. The author reports that five widely deployed agent workflow frameworks answer "what does resume mean for effects that already fired?" differently, and none exposes a machine-checkable contract. One finding: LangGraph 1.2.9 re-executed durably recorded work after a real SIGKILL. That makes it exactly-once across interrupts but at-least-once across crashes, on the same API.

Failure stage: execute (persistence / resume)

DEV Community · Sven Schuchardt · 2026

"Every AI agent failure I've debugged in 2026 was an idempotency problem"

A practitioner write-up of production incidents: one customer received the same onboarding email fourteen times in nine minutes, a B2B account was charged twice for one subscription renewal, and one order appeared in the order system as three. The common thread is agents that retry on timeouts, 5xx errors and ambiguous tool responses, against tool calls never designed to be retried.

Failure stage: execute (surfaced at output)

The hidden connection

The three sources look at different layers: model behaviour, persistence semantics and production tickets. They agree on where the fix lives. When the system can observe the outcome, a good model behaves. When it can't, only the contract (idempotency keys, deduplication at the boundary, an honest resume semantics) prevents the echo. The harness you picked and the model you upgraded to are mostly noise.

06Argue the Other Side

The strongest objection: the model does matter. In the recoverable case, Li's numbers show weaker models duplicating far more often than frontier ones, so a model upgrade is a real fix for part of the problem. That's true. If most of your faults are lost acknowledgements with a working read path, a better model plus an "act exactly once" instruction buys a lot.

But you don't get to choose which faults you have. Timeouts during provider incidents are exactly the "still in flight" case where the model can't win, and they arrive in bursts, on your busiest day. A second objection is cost: threading idempotency keys through every write tool is real work, and some downstream APIs don't accept them. Then you need a deduplication store on your side of the boundary. It's more code, but the alternative is a support queue.

08The Fix: Triage Checklist

  • List every tool that mutates external state. For each, record: does it accept an idempotency key? Is there a read-back?
  • Derive keys deterministically from run_id, step index and canonical arguments, never from a random UUID generated per attempt.
  • Put a dedup store (key → result) in front of writes whose downstream API has no key support.
  • Make the "outcome unknown" state explicit in the tool result, rather than a generic error string the model will reinterpret.
  • Count side effects, not tool calls, in your traces: one business action should map to one external effect.
  • Chaos-test resume: SIGKILL the worker between "write sent" and "checkpoint saved", then resume and diff the external state.

The guard is small and harness-agnostic, which matches the finding that a key-attaching guard transfers across harnesses unchanged:

# wrap every state-mutating tool once, at registration time
import hashlib, json

def idempotent(tool, store):
    def call(run_id, step, **args):
        key = hashlib.sha256(json.dumps(
            [run_id, step, tool.__name__, args], sort_keys=True).encode()).hexdigest()
        if (prior := store.get(key)) is not None:
            return prior                      # echo suppressed
        result = tool(**args, idempotency_key=key)
        store.put(key, result)
        return result
    return call

09Recall Check

Why can't a better prompt fix duplicates when a request is still in flight?

Because the agent has no information about whether the first write landed. It's choosing between a duplicate and a skipped step blind. Only the contract (keys, dedup, read-back) changes what it can know.

In Li's Limbo study, what explained most of the variance when outcomes were unobservable?

The tool contract, at 81%. The model explained most of the variance only when a read-back could reveal the outcome.

What does "exactly-once across interrupts, at-least-once across crashes" mean for your agent?

A planned pause and resume is safe, but a worker crash can replay a step whose side effects already fired. Every write in that step can echo.
