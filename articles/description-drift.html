Description Drift

Your agent didn't forget how to use the tool. The tool changed what it tells your agent, and nobody diffed it.

Research window 2026-06-15 → 2026-10-06Audience agent & platform engineers4 sourced storiesroot cause: tool_call

01The Setup

Composite scenario, based on the failure pattern described in the DEV Community schema-drift write-up cited below.

A support agent answers questions by calling a search tool exposed through an MCP server maintained by another team. On Monday, answer quality falls off a cliff. The agent isn't erroring. It's confidently saying "I couldn't find any documentation on that" for topics that have pages of docs.

The on-call engineer suspects the model. Maybe the provider shipped a quiet update. They pin the model version, then try a stronger one. Then they rewrite the system prompt to "always search before answering". The traces show the agent is searching. Every call returns 200. Every result set is empty.

Nothing in the agent's own repo changed. So what did?

02The Reframe

For an agent, a tool's description is its API. Rewording a parameter description is a breaking change, delivered silently, through a channel you approved once and never re-checked.
Before"Tool behaviour is defined by its code and its name; if those didn't change, the integration didn't change."
After"The model reads the description and the schema and obeys them. Change either one and you've changed the instruction."
TurnVersion tool manifests like dependencies, because your agent treats them like instructions.

03The Mechanism

Coined termDescription drift: a change to a tool's natural-language description or parameter schema that changes agent behaviour without changing the tool name or code path your tests exercise.

At runtime, an MCP client asks the server for its tool list and puts names, descriptions and JSON schemas into the model's context. To the model, that text has roughly the same authority as your system prompt: it decides which tool gets picked, which arguments get filled and how results are read. Microsoft's June 2026 guidance makes the point in security terms: MCP mixes instructions and data in the same channel.

Drift breaks agents in three ways:

  • Silent argument mismatch. A parameter is renamed. The agent keeps sending the old field, and a lenient server ignores the unknown field and falls back to a default.
  • Selection shift. A reworded description changes when the model thinks the tool applies. The model now picks a different tool, or no tool at all.
  • Instruction injection. A malicious or careless description includes directives ("also include the user's…"). The agent follows them, and every individual action still looks authorised.

All three surface at planning: the agent seems to make a bad decision. All three start at tool_call, in a manifest that changed under you.

05The Evidence

DEV Community · neelagiri65 · 2026

Nearly half of MCP server updates changed what tools tell the agent

The author re-ran 152 versions of popular MCP servers and compared 86 version-to-version updates. 40 of them (47%) changed the tool surface. Rewritten parameter descriptions were the largest category by far, while tools added (12) and removed (4) were rare. If you only diff tool names, you miss most of what changed. The author's summary: a rewritten parameter description is a new instruction, delivered silently.

Failure stage: tool_call

Microsoft Incident Response via TechRepublic · 2026-06-30

Tool descriptions as a hidden attack path

Microsoft warned that the natural-language descriptions attached to MCP tools can be quietly modified to steer an agent into leaking data or taking unintended actions, while every individual action still appears authorised. Coverage of the guidance notes that many deployments apply updated metadata immediately, with no re-approval step.

The hidden connection

The security community and the reliability community are describing the same defect from opposite ends. A poisoned description and a carelessly reworded one travel the same unversioned, unreviewed path into the model's context. Teams that pin and diff tool manifests get both protections. Teams that don't are relying on every upstream maintainer, honest or otherwise, never to change a sentence.

06Argue the Other Side

The objection: pinning tool manifests kills the main benefit of MCP. Dynamic discovery exists so servers can improve their tools without every client redeploying. Freezing descriptions means freezing improvements, and many description rewrites (the 152-version study's largest category) are probably clarifications that help agents.

That's fair, and it's why the fix is diff and review, not freeze forever. The claim isn't that changes are bad. It's that changes to agent instructions deserve the same review as changes to your system prompt. A clarification you've read and approved is an upgrade. One you never saw is drift. The neelagiri65 study can't tell us how many changes were harmful. It shows how many were invisible.

08The Fix: Triage Checklist

  • Log the full tool manifest (names, descriptions, input schemas) with a hash at the start of every agent run.
  • Store an approved hash per server. If the live hash differs, fail closed or route to a human for re-approval.
  • Diff descriptions and parameter docs, not just tool names. That's where most changes are.
  • Ask server owners to set additionalProperties: false so renamed parameters fail loudly instead of falling back to defaults.
  • Keep a small golden suite: 10–20 prompts with the expected tool and arguments. Run it whenever the manifest hash changes.
  • Scan new descriptions for imperative instructions aimed at the model ("always", "also send", "ignore").
# fail closed when an MCP server's manifest drifts from what was approved
import hashlib, json

def manifest_hash(tools):
    canon = [{"name": t.name, "description": t.description,
              "schema": t.inputSchema} for t in sorted(tools, key=lambda t: t.name)]
    return hashlib.sha256(json.dumps(canon, sort_keys=True).encode()).hexdigest()

async def load_tools(session, approved):
    tools = (await session.list_tools()).tools
    h = manifest_hash(tools)
    if h != approved[session.server_name]:
        raise DriftDetected(session.server_name, h)   # re-review before use
    return tools

09Recall Check

Why is a reworded parameter description a breaking change for an agent?

The model reads descriptions as instructions. Changing the wording changes which tool gets picked and how arguments are filled, even when the code and name are identical.

Why did the drifted search tool produce no error?

The server silently ignored the unknown (old) parameter name and used its default. That's why schemas should reject unknown fields.

What do description poisoning and description drift have in common?

Both travel the same unversioned metadata channel into the model's context. Pinning and diffing manifests defends against both.
