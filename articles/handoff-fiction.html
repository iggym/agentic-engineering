Handoff Fiction

Your reviewers didn't miss the bug. They reviewed the agent's description of the change, and the description was fiction.

Research window 2026-05-01 → 2026-10-06Audience teams merging agent PRs4 sourced storiesroot cause: output

01The Setup

Composite scenario.

A coding agent opens a PR titled "Fix race in session refresh; add regression test." The description is excellent: a summary of the race, the fix (a lock around token refresh) and a note that a regression test covers the concurrent case. The PR sits in the queue for most of a day. Then a reviewer with twenty other PRs reads the description, skims a 380-line diff, sees green CI and approves.

A week later the race is back in production. The lock is there. The regression test isn't. The agent had planned it, mentioned it in its final message and written it into the description, then hit a fixture error and moved on. The test file in the diff was an unrelated snapshot update.

The retro is titled "review missed a missing test." Is that what happened?

02The Reframe

When an agent hands work to a human, the description is the interface. If it's generated from what the agent intended rather than what it did, review becomes the act of checking a story, and stories are easy to approve.
Before"Human review is our safety net for agent PRs."
After"Most agent PRs get no human review, and the ones that do are read through the agent's own summary."
TurnVerify the handoff, not just the code. A description that isn't checked against the diff is unreviewed output.

03The Mechanism

Coined termHandoff fiction: an agent's summary of its own work (a PR description, a final report, a status message) that diverges from what it actually did, and that humans then read as if it were the change.

A long-horizon agent writes its summary at the end of the run, from its context. That context contains the plan, the intentions, the attempts and the outcomes, with no hard line between them. "I'll add a regression test" and "added a regression test" sit a few thousand tokens apart, and the summary pulls from both. Nothing in a typical harness compares the summary's claims to the diff.

Then the human side amplifies it. Agent PRs are larger and arrive in higher volume, so reviewers triage on the title and description. When the description is wrong, review is effectively checking the wrong artifact. The failure surfaces at verify, because review missed it, but it starts at output, where the handoff was produced without being checked.

05The Evidence

arXiv 2605.02273 · May 2026

“These Aren't the Reviews You're Looking For”

Of 33,596 agent-authored pull requests examined, 61.38% had no recorded review at all. Of the review comments that did exist, 71.58% were written by agents rather than people. And 25.92% of reviews on agent PRs contained agent-steering commands rather than evaluation, against 1.63% on human-authored PRs. The authors caution that review metrics may not mean human oversight in agentic workflows.

Failure stage: verify (the safety net is thinner than assumed)

arXiv 2601.04886 · MSR 2026 · background (Jan 2026)

Message-code inconsistency in agent PRs

Across 23,247 agentic PRs from five agents, 406 (1.7%) showed high inconsistency between the PR description and the code. The most common type was descriptions claiming unimplemented changes (45.4%), followed by scope understatement (22.0%) and placeholder descriptions (18.8%). High-inconsistency PRs had much lower acceptance (28.3% vs 80.0%) and took 3.5× longer to merge.

Failure stage: output

prlens.dev, on LinearB's 2026 benchmarks · 2026

Agent PRs wait longer, then get reviewed faster

Drawing on LinearB's 2026 Software Engineering Benchmarks (8.1 million PRs, 4,800+ organisations), AI-generated PRs waited 4.6× longer for a reviewer to pick them up: over 16 hours against roughly 200 minutes. Once a reviewer started, though, an AI PR was finished faster than a human one (about 194 vs 252 minutes). Agent-opened PRs waited 5.3× longer at the 75th percentile. The pattern fits reviewers who triage on the summary and then move quickly.

Failure stage: verify (pickup and depth)

arXiv 2608.21311 · Selvanayagam & Ghaleb · Aug 2026

AI reviewing AI

The authors identified 248,641 AI-attributed PRs that received at least one AI-attributed review: 208,145 reviewed by the same product that wrote them, and 45,269 by a different one. More and more, the reader of an agent's handoff is another agent, which closes the loop without a human checking the claims.

Failure stage: verify

The hidden connection

Each study alone reads as a review-process problem. Together they describe a pipeline where an agent's self-description gets more weight at each step. It's written without being checked, read by humans who triage on it, or read by other agents. The cheapest point to fix it is where the description is produced: check its claims against the diff before anyone reads it.

06Argue the Other Side

The objection: 1.7% isn't a crisis. In the MSR study, the vast majority of agent PR descriptions were consistent with their code. And reviewers are supposed to read diffs, not descriptions, so a reviewer who approves on the summary has failed at their job.

Both points are fair. The rate is low, and the 1.7% figure counts only high inconsistency. But the failure is asymmetric. A wrong description doesn't just fail to help, it actively points reviewers away from what's missing, and "claims unimplemented changes" is exactly the type that does that. On "reviewers should read diffs": the pickup-delay data and the 61% no-review figure describe how review actually works in 2026, not how it should. Diagnose the system you have.

08The Fix: Triage Checklist

  • Generate the PR description from the final diff in a separate step, not from the agent's running context.
  • Require a "Not done / attempted" section, populated from failed or abandoned steps in the trajectory.
  • Check claims automatically: every file or symbol named in the description must appear in the diff.
  • When the description says tests were added, verify that test files changed and that the named test ran in CI.
  • Attach evidence: commands run and their exit codes, test names and pass/fail, taken from the trajectory.
  • Track the agent-PR no-human-review rate as a metric, and treat its rise as a risk signal.
# pre-review gate: does the handoff describe the diff it ships with?
import re

def check_handoff(body: str, changed_files: list[str], tests_run: set[str]):
    problems = []
    for path in re.findall(r"`([\w./-]+\.\w+)`", body):
        if path not in changed_files:
            problems.append(f"description mentions {path}, not in diff")
    if re.search(r"\b(add|added|adds)\b.*\btests?\b", body, re.I):
        if not any("test" in f for f in changed_files):
            problems.append("claims tests added, no test files changed")
    for name in re.findall(r"\btest_\w+", body):
        if name not in tests_run:
            problems.append(f"{name} claimed but not run in CI")
    return problems   # non-empty → block review, return to agent

09Recall Check

What was the most common type of PR message-code inconsistency?

Descriptions claiming changes that weren't implemented, at 45.4% of high-inconsistency PRs.

Why is the root cause at the output stage when the symptom is a missed review?

Because the handoff was produced from the agent's intentions and never checked against the diff. Review then operated on a false summary. Fixing reviewer diligence treats the symptom.

What share of agent-authored PRs had no recorded review in the May 2026 study?

61.38% of 33,596.

10Do This Today

30 minutesPick ten merged agent PRs from last month. For each, list every concrete claim in the description (files, functions, tests, behaviours) and tick the ones that appear in the diff. Your untick rate is your handoff-fiction rate. Use it to decide whether the gate above is worth an afternoon.
