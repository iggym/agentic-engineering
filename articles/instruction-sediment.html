Instruction Sediment

Your agent isn't ignoring your rules. It's obeying all of them, including the ones whose reason left the team months ago.

Research window 2026-07-01 → 2026-10-06Audience teams using coding agents3 sourced storiesroot cause: retrieval

01The Setup

Composite scenario.

A team's coding agent keeps doing something strange: every new API handler gets wrapped in a hand-rolled retry helper that the team deprecated in spring. Reviewers delete it, then the next PR brings it back. Someone opens CLAUDE.md and finds the cause on line 212: "Always wrap outbound calls in withRetry()."

Nobody remembers who added it or why. It might have been an incident workaround. It might still matter for one legacy service. The file is 400 lines long, and every line looks like this one: confident, imperative, unexplained. Deleting it feels risky, so they add line 401: "Do NOT use withRetry() for new handlers." Now the agent has two rules that contradict each other.

The behaviour shows up in execution. Where does it start?

02The Reframe

An instruction file is a retrieval system with no eviction policy. Rules go in for a reason, the reason never gets written down, and so nothing ever comes out. The agent faithfully loads all of it on every run.
Before"The agent ignores CLAUDE.md, so we need stronger wording, capital letters, more rules."
After"The agent obeys a file full of orphaned rules that nobody dares delete."
TurnYour context file needs a garbage collector, and the only one that works is recorded rationale.

03The Mechanism

Coined termInstruction sediment: agent instructions whose rationale has been lost, so they can't be safely removed and keep loading into every run's context.

The asymmetry is simple. Adding a rule after the agent makes a mistake costs one line and a minute. Removing a rule safely means knowing which past mistake it prevents. If you don't know, you'd have to test every combination of remaining rules to rule out a regression. Chakrabarti's August 2026 paper formalises this: appending is O(1), deleting without risking a regression is O(2ⁿ). Files grow without bound.

The cost lands at the retrieval stage, because a context file is retrieval: it's pulled into the prompt on every run, unconditionally, whether or not the task needs it. Each orphaned rule is a little irrelevant context. Some are actively wrong. Contradictory pairs force the model to guess which one wins. The resulting behaviour looks like an execution bug or a model quirk, so teams respond by adding more rules.

05The Evidence

arXiv 2608.11095 · Kushal Chakrabarti · Aug 2026

“Why Does CLAUDE.md Keep Growing? Catastrophic Remembering in Agentic Coding”

Across 247,694 instruction lifetimes in 1,867 GitHub repositories, agent instruction files grew until the history ended or someone rewrote the whole file. After a rewrite they grew back faster: +4.1% instructions per commit before a rewrite, +4.9% after. The paper's proposed fix is cheap. Write the rationale down as a comment next to the rule at the moment you add it. The paper reports that this removes 99.3% of the excess growth.

Failure stage: retrieval (what gets loaded, and why it never leaves)

Generative Labs · Prakhar Khatri · Jul 2026

“CLAUDE.md Files Make Coding Agents Cheaper, Not More Correct”

A controlled 288-attempt ablation ran Claude Code and Codex on the same tasks and repositories, scored against each repo's own known-good tests, varying only how project instructions were supplied. It found no measurable correctness gain from context files. The repositories' real instruction files never turned a near-miss into a pass, on either agent. The efficiency gains that earlier work reported are real. The correctness gains didn't show up.

Failure stage: retrieval

MSR 2026 study of 466 projects, via usewire.io · 2026

Half of AGENTS.md files are never updated after the first commit

A study accepted to the Mining Software Repositories conference scanned 10,000 active repositories (about 5% had adopted an AI context file) and analysed 155 AGENTS.md files in depth. It identified five ways developers write agent context. It also found that half of the files are never updated after the commit that created them. The format exists, but the practice of maintaining it mostly doesn't.

Failure stage: retrieval (staleness)

The hidden connection

The three studies measure different things: growth, correctness and staleness. Together they describe one lifecycle. Files are written once (MSR), appended to forever without rationale (Chakrabarti), and the result doesn't buy the correctness teams assume it does (Khatri). Earlier in 2026, ETH Zurich's evaluation found context files raised inference cost by over 20% without improving success rates. Sediment is how you pay that cost.

06Argue the Other Side

The counter-argument has data behind it. Lulla et al. measured AGENTS.md files cutting median agent runtime by 28.64% and output tokens by 16.58%. Khatri's study is consistent with that: cheaper, not more correct. Cheaper is worth a lot at scale, and a good context file clearly encodes useful conventions.

So this isn't an argument to delete your context file. It's an argument against an unmaintained one. The efficiency win comes from accurate, relevant facts about the repo. Sediment, meaning rules that are stale, contradictory or unexplained, is the part that adds tokens without adding accuracy. The open question, which none of the sources settles, is how much of a typical file is sediment. The 50% never-updated figure suggests it's a lot.

08The Fix: Triage Checklist

  • Count the lines in your agent instruction files and chart them against git history. Is the line going up and to the right?
  • Require a why: comment on every new rule: the incident, PR or constraint it exists for.
  • Add an owner and an added-on date, so a quarterly prune has something to go on.
  • Search for contradictory pairs (always/never on the same subject) and resolve each one to a single rule.
  • Move subsystem-specific rules into scoped files near that code, rather than loading them on every run.
  • Before deleting a rule, run your eval set with and without it. Rationale tells you which evals to run.
# ci/lint_agent_rules.py — fail the build on rules without recorded rationale
import re, sys, pathlib

RULE = re.compile(r"^\s*[-*]\s+(always|never|do not|must|don't)\b", re.I)
bad = []
for path in ["CLAUDE.md", "AGENTS.md"]:
    lines = pathlib.Path(path).read_text().splitlines() if pathlib.Path(path).exists() else []
    for i, line in enumerate(lines):
        nxt = lines[i + 1] if i + 1 < len(lines) else ""
        if RULE.match(line) and "why:" not in line + nxt:
            bad.append(f"{path}:{i+1}: {line.strip()}")
if bad:
    sys.exit("rules missing a why: comment\n" + "\n".join(bad))

09Recall Check

Why does an instruction file grow without bound?

Adding a rule is O(1). Safely deleting one without knowing its rationale means ruling out regressions across combinations of the remaining rules, which is O(2ⁿ). Nobody pays that cost, so nothing gets deleted.

What did the 288-run ablation find context files improve, and not improve?

No measurable correctness gain. Earlier work found real efficiency gains in runtime and tokens. The upshot: cheaper, not more correct.

What single practice did Chakrabarti find removed almost all excess growth?

Writing the rule's rationale down as a comment when you add it. The paper reports this removes 99.3% of the excess.

10Do This Today

30 minutesOpen your largest agent instruction file and pick the ten oldest rules (git blame helps). Next to each, write the reason it exists. Any rule you can't explain in one line is sediment. Open a PR that deletes it and let your eval suite argue back.
