Never Committed

April 15, 2025 · Agent memory & state

The Setup

A LangGraph agent running a multi-source research task executes three tool calls in sequence: a web search, a document retrieval, and a database query. Each returns structured results. The agent then synthesizes a final answer. The answer contradicts the web search results from step one — not in a nuanced way, but in a way that suggests the agent never saw them at all.

The developer checks the tool-call logs. All three calls returned 200. The search results are right there in the raw response payload. They increase the context window. They switch to a model with a larger token limit. The bug persists. They add retry logic. The bug persists. They insert a summarization step after each tool call to compress context. The bug still persists across multiple runs, always dropping the same early-step data.

The problem was never the context window. The problem was in the state channel's merge function — a single default that silently discarded data on every run.

The Reframe

Your agent didn't run out of context. Your state layer never committed.

What looks like context collapse — an agent "forgetting" earlier information, contradicting itself, or looping on already-resolved subproblems — is almost always a state-commit failure. The information entered the system. It was processed. It was never persisted in a form that survived the next state transition.

The Wiring

Engineers treat context window size and state architecture as separate problems. They're the same failure surface, viewed from different angles. The context window is the delivery mechanism — it determines how much information can be presented to the model in a single turn. State architecture is the commit protocol — it determines which information survives between turns. A 200K-token window with a broken commit protocol doesn't give you more memory. It gives you a larger buffer of uncommitted data that evaporates on the next merge.

This is why upgrading the model or increasing the context window doesn't fix these failures. You're expanding the buffer without fixing the commit. The data enters, gets processed, and gets overwritten before the model ever needs it again. You can verify this in your own system: run the same agent task twice, once with all tool results concatenated into a single state field, and once with each result in a separate field. If the single-field version fails more often, your merge strategy is the culprit, not the model.

Every "context collapse" you've debugged was actually a state-commit failure wearing a token-limit disguise.

The same pattern appears across every agent framework — different implementations, identical failure mode. The surface symptom is always the same: the agent makes a decision that ignores information it received earlier. The knee-jerk diagnosis is always "not enough context." The actual root cause is always in the state layer — how information flows from tool output into the state object that the model reads on its next turn.

The Evidence

Tracing the LangGraph failure through its execution layers makes the mechanism mechanical, not theoretical:

Planning. The agent receives the research task, decomposes it into three sub-queries, and decides to call the web search tool first. State: {messages: [task], tool_results: []}.

Tool Call. The web search executes successfully, returning relevant results. The raw response is in the tool-call log. State should now include tool_results: [search_results_A].

State Commit. LangGraph's state channel receives the tool result and merges it into the agent's state. Here's the failure: the tool_results field uses the default reducer, which replaces the entire field value. When the document retrieval returns results next, tool_results is overwritten with [doc_results_B]. The search results are gone. No error. No warning. No log entry. The state object silently shrank.

Retrieval. On the next planning step, the model reads the current state. It sees tool_results: [doc_results_B, db_results_C]. It doesn't know it's missing data — from the model's perspective, the state is complete and consistent.

Output. The final synthesis is built on incomplete state. It contradicts the first tool's results because those results aren't in the state anymore. The model didn't forget. The state layer never committed them.

LangGraph's documentation states that "by default, the new value will override the existing value" for state channels. This isn't a bug — it's the documented default. The fix is changing one line: specifying an append reducer instead of accepting the default.

Anthropic's "Building effective agents" guidelines, live since late 2024 and widely referenced by April 2025, frame this as an architecture concern: design your state schema to carry forward what matters, rather than assuming the model will extract it from raw conversation history. State design is a first-class engineering decision.

Public user reports about Cognition AI's Devin, documented across X/Twitter and blog posts through March and April 2025, described a consistent pattern on long-horizon tasks spanning 15–25 steps. Correct decisions made early were contradicted later. One widely-circulated example: a multi-file refactoring where Devin correctly identified a shared dependency pattern in step 3, then introduced an import that broke that pattern at step 19 — not because the model couldn't maintain the pattern, but because the decision wasn't surfaced in the state presented at step 19.

The strongest counterargument: "But sometimes the context window genuinely is too small — token limits are real." True, but token limits are a ceiling you hit once and fix by upgrading; state-commit failures are a floor you fall through on every run and fix by changing one line of reducer configuration. If your agent fails the same way on a 32K window and a 200K window, it's not a token problem.

The Fix

State-commit failures are deterministic. They reproduce on every run. That makes them unusually easy to diagnose — if you know where to look. Most frameworks default to replacement semantics because it's the simplest correct behavior for a single-value field like current_step. The problem arises when developers use the same default for collection fields like tool_results or discovered_facts — fields that should accumulate, not replace.

Audit your merge semantics — print full state before and after every merge; look for fields that shrink between steps
Map replace vs. append — document which state fields use replacement and which use accumulation; any field that should grow must use an append reducer
Checkpoint at decisions — add explicit state snapshots at decision points, not only after tool calls
Run a recall test — give your agent a task where step 15 must reference a fact from step 3; if it fails, your state layer is dropping data
Diff state, not prompts — when debugging, diff the state object between steps; the prompt is a rendering, the state is the source of truth
