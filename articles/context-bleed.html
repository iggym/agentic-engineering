context bleed

Bold reframe: Your context isn't isolated — it's a shared wound that infects every subagent. Context bleed is the invisible contamination that spreads from one task to another through shared memory.

Opening scene – AutoGPT memory pollution, Jan 2026

The agent planned a memory write (PLANNING), called `memory_write` (TOOL CALL), but the retrieval context lacked a namespace (RETRIEVAL). It executed the write to a shared global store (EXECUTE), verify checked only that the write succeeded (VERIFY), and output passed (OUTPUT). Root cause: RETRIEVAL (no isolation). First visible: VERIFY (didn't check namespace). The verify stage never asked "whose context is this?"

"Shared context is the silent killer of multi-agent systems — it rots from one task to another before anyone notices."
— coined term context bleed

the hidden connection

Isolated context = debuggable system. Shared context = silent corruption.

credibility & nuance

AutoGPT's postmortem cited the specific memory_write call that overwrote the `user_pref` key. CrewAI's fix isolated per-agent context dicts. The strongest counterargument: "we use unique keys." But unique keys don't prevent one agent from reading another agent's key if the namespace is flat. That's context bleed — not key collision, but namespace pollution.

🔧 triage checklist (trace each item to its stage)

  • PLANNING – does the plan name a context namespace?
  • RETRIEVAL – is context scoped per task?
  • EXECUTE – does write include a namespace?
  • VERIFY – does verify check context source tags?
